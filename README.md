Для работы с друзьями нужно несколько простых правил.

КОМАНДЫ ДЛЯ DJANGO 
1. python manage.py runserver (запустить  сайт)
2. python manage.py check (проверяет на наличие ошибок)
3. python -m venv .venv (ВАЖНО всегда должна быть папка .venv что бы вообще могли работать с джанго)
4. дальше надо в .venv/Scripts/ и скопироввать путь activate.bat/ps1

## 1. Всем дать доступ
GitHub → репозиторий → **Settings → Collaborators → Add people**. Без этого друзья не смогут пушить в твой репозиторий, только присылать форки.

## 2. Каждый работает в своей ветке
Это главное, что избавляет от «rejected / fetch first». Не пушьте все в `main`.

```bash
git checkout main
git pull                      # взять свежее
git checkout -b feature/leaderboard   # своя ветка под задачу
# ...работа, коммиты...
git push -u origin feature/leaderboard
```

Дальше на GitHub открываете **Pull Request** в `main`. Кто-то из вас смотрит изменения и нажимает Merge. Так `main` всегда рабочий.

## 3. Ежедневный цикл
```bash
git pull                  # перед началом работы
# работа
git add <файлы>           # не `git add .` вслепую
git commit -m "что сделал"
git pull                  # перед пушем, подтянуть чужое
git push
```

## 4. Если пуш отклонён (как у тебя было)
Значит, кто-то успел запушить раньше. Нужно подтянуть его изменения:

```bash
git pull --no-rebase      # слить чужое с твоим
# при конфликте: откройте файл, оставьте нужное, удалите <<<<<<< ======= >>>>>>>
git add <файл>
git commit
git push
```

`--force` и `--force-with-lease` не используйте, они затирают чужие коммиты. Строка про это в твоём `docs.txt` для командной работы не подходит.

## 5. Как не мешать друг другу
- **Договоритесь, кто какие файлы трогает.** Например, друг только CSS и шаблоны, ты `views.py`. Тогда конфликтов почти не будет.
- **Коммиты маленькие и часто.** Лучше пять мелких, чем один огромный.
- **Не коммитьте `db.sqlite3` и `.pyc`.** Теперь они в `.gitignore`. У каждого своя база, после `pull` достаточно `python manage.py migrate`.
- **Миграции коммитьте.** Если вы оба меняете модели, будут конфликтующие миграции с одним номером, поэтому о моделях договаривайтесь заранее.
- **Секреты и пароли не пишите в файлы репозитория.**

## Почему без конфликтов не вышло
Твоя история и история на GitHub разошлись: одни и те же изменения (дизайн, `.gitignore`) закоммичены дважды под разными хешами. Поэтому `pull` всё равно дал конфликты в 6 файлах, и их пришлось разрешать вручную.

## Что я сделал и какими командами

ЕСЛИ ПОЯВИЛИСЬ КОНФЛИКТЫ

1. **Проверил состояние.**
   `git status --short` показал, что слияние уже было начато и не закончено. `git branch -a` и `git remote -v` показали ветки и адрес репозитория. `git fetch` скачал чужие коммиты без слияния. `git log --oneline HEAD..origin/main` показал, чего у тебя нет, а `git diff --stat HEAD origin/main` показал, какие файлы различаются.

2. **Отменил незаконченное слияние:**
   ```bash
   git merge --abort
   ```
   Рабочее дерево стало чистым. Осталась только неотслеживаемая `db.backup.sqlite3`.

3. **Сделал pull:**
   ```bash
   git pull --no-rebase --no-edit
   ```
   `--no-rebase` сливает ветки, а не переписывает твои коммиты. `--no-edit` не открывает редактор для сообщения. Появились конфликты в README.md, main.css, game.html, logo.html, main.html и signUp.html.

4. **Разрешил конфликты, как ты выбрал (твой дизайн):**
   ```bash
   git checkout --ours <файлы css и html>
   ```
   Эта команда берёт твою версию файла целиком. Для README команда была другой:
   ```bash
   sed -i -e '/^<<<<<<< /d' -e '/^=======$/d' -e '/^>>>>>>> /d' README.md
   ```
   Она удаляет строки-маркеры конфликта, и в файле остаются оба текста.

5. **Добавил `db.backup.sqlite3` в `.gitignore`** командой `printf '...' >> .gitignore`.

6. **Зафиксировал результат:**
   ```bash
   git add README.md .gitignore jewpro/bibok
   git commit -m "Merge origin/main: keep local design, merge README"
   ```
   `git add` помечает конфликты решёнными, `git commit` завершает слияние.

## Что дальше
- Чтобы отправить результат на GitHub: `git push`. Теперь он пройдёт без `--force`, потому что слияние включает все чужие коммиты.
- Дизайн друга (простой, «Guess the movie») в рабочие файлы не попал, но остался в истории `origin/main`. Предупреди друга, чтобы он сделал `git pull` и не перезаписал твой дизайн.
- Чтобы не повторять это в будущем, работайте в отдельных ветках и пушьте только после `git pull`.
